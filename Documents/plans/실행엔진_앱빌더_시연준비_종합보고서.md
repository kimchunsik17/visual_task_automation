## 요약

이번 검토에서 확인한 가장 중요한 사실은, 남은 과제들이 병렬 목록이 아니라 **세 개의 기둥에서 파생되는 하나의 줄기**라는 점이다. 그 셋은 (1) 실행 엔진의 코드 생성 → 디스패처 전환, (2) Run/Step 실행 상태 모델, (3) "사용자 제공 필드" 선언 스키마다. 이 셋이 서면 노드별 재시도, 부분 실행 개선, 앱의 구조화 출력 바인딩, 진행률 스트리밍, T1(템플릿 일반 필드) 해결, 워크플로우→앱 자동 폼이 전부 그 위에서 저렴하게 열린다.

또 하나의 확인 사항: `compile_workflow`가 이미 부분 실행(`entry_node_id`/`stop_node_id`/`scope_node_ids`)과 데이터 피닝(`pinned_outputs`)을 지원하고, 승인 스냅샷 재개(ADR-0015)도 있다. 즉 "일시정지 가능한 실행"의 개념 설계는 절반쯤 되어 있으며, 문제는 그것이 `exec()` 기반 코드 생성 위에 올라가 있어 노드 단위 개입 지점이 없다는 것 하나로 수렴한다.

단기적으로는 다음 주 수~금 시연회(부스 형식)가 우선순위를 정한다. 이번 주는 새 구현 대신 시연 안정화(승인키, 대기 템플릿 승인, 피닝 백업, 부하 리허설)에 쓰고, 부스에서 관측한 방문자 반응을 §1·§2의 착수 순서 조정에 쓴다.

## 1. 실행 엔진 개선 — 4단계

순서 자체가 의존 관계다: 2는 1 없이 노드 경계가 없고, 3의 재개는 2 없이 불가능하며, 4의 재시도는 1·2가 전제다.

### 1.1 (1단계) 코드 생성 → 그래프 인터프리터(디스패처) 전환

현 구조의 근본 한계는 보안 이전에 **개입 지점의 부재**다. `compile_workflow`가 파이썬 소스를 만들고 `run_workflow`가 `exec()`하는 방식에서는 노드 하나가 실행되는 순간에 엔진이 끼어들 수 없어, 노드별 재시도·타임아웃·단계별 상태 저장·중간 로그 스트리밍이 전부 불가능하다. 목표 구조는 노드 타입 → 비동기 executor 함수 매핑이며, 매핑은 `node_definition`에서 파생시킨다(N1·N2 결함의 교훈 — 손으로 적은 목록 금지). 엔진은 `compile_workflow`와 동일한 순회 규칙(트리거 루트 판정, `targetHandle` 구분, tool 노드 제외, 첨부 간선 예외)을 재사용하되 코드를 만들지 않고 직접 `await`한다.

기존 entry/stop/scope/pinned 파라미터는 엔진 인자로 그대로 승계된다. 지금은 "순회할 간선을 잘라내는" 방식으로 구현되어 있으나 인터프리터에서는 자연스러운 실행 제어가 되어 오히려 단순해진다.

이관 전략은 빅뱅을 피한다. 첫째, 노드 단위로 생성기 → executor를 이식하되 미이식 노드는 기존 생성 코드를 감싼 임시 executor로 하이브리드 운영한다. 둘째, **섀도 실행으로 등가성을 검증한다** — 커뮤니티 템플릿 242종 + mock 시나리오 + `test_official_templates.py` 508건이 코퍼스다. 두 엔진을 mock 모드로 나란히 돌려 출력·로그·토큰 집계를 대조한다. 셋째, `/api/features` 인프라로 프로젝트별 feature flag 점진 전환한다.

`pythonNode`는 별도 취급한다. AST 허용 목록은 유지하되 실행을 자식 프로세스(rlimit, 시간 제한, 네트워크 차단)로 격리한다 — n8n 2.0 Task Runner와 같은 패턴이며, 백로그 13번(커뮤니티 노드 SDK)의 전제 인프라가 된다.

**주의**: 병렬 분기 실행 등 실행 순서 의미론을 바꾸는 최적화는 등가성 검증 완료 전에 하지 않는다. 순서가 바뀌면 242종 코퍼스가 대조 기준으로서 가치를 잃는다.

### 1.2 (2단계) 실행 상태 영속화 — Run/Step 모델

디스패처가 생기면 노드 경계마다 기록한다.

```
workflow_runs: id, project_id, trigger_source, status(queued/running/paused/succeeded/failed),
               idempotency_key(unique), started_at, finished_at, error_summary
run_steps:     run_id, node_id, attempt, status, output_ref, tokens, started_at, finished_at
```

이것으로 세 가지가 한 번에 풀린다. 승인 대기 전용이던 스냅샷 재개가 일반화되고(승인·wait 노드·워커 재시작이 같은 메커니즘), `/api/projects/{id}/runs`의 실행 이력이 노드 단위 타임라인으로 풍부해지며, step 기록을 SSE(`message_stream.py` 재사용)로 흘리면 에디터의 실시간 노드 진행 표시가 된다. 현재는 실행 종료 후 `__execution_logs__`를 일괄 수신한다.

### 1.3 (3단계) 큐와 워커 분리

`run_workflow`는 현재 API 핸들러·APScheduler·텔레그램 봇·웹훅 등 7개 지점에서 동기 호출된다. 권장 구조는 **PostgreSQL 기반 큐**다 — `SELECT ... FOR UPDATE SKIP LOCKED`. Redis/Celery를 먼저 권하지 않는 이유는 이미 PostgreSQL이 있고, 단일 VM 배포 규모에서 새 인프라 하나는 운영 부담 하나이기 때문이다. `enqueue/dequeue` 인터페이스만 추상화해 두면 처리량이 문제될 때 Redis로 교체하는 비용이 작다.

실행 경로는 이원화한다. 에디터 수동 실행·dry-run은 지금처럼 인라인 즉시 실행(타임아웃 부여)으로 반응성을 지키고, 스케줄·웹훅·트리거·배포 앱 실행은 큐로 보낸다. 스케줄러는 APScheduler를 워커 리더 하나로 옮기거나, `schedules.next_fire_at`을 워커가 같은 SKIP LOCKED로 폴링하게 하여 다중 인스턴스에서 cron 중복 발화를 막는다.

내구성 규칙: 워커는 run에 heartbeat를 찍고, heartbeat가 끊긴 `running` run은 다른 워커가 회수해 — step 기록 덕분에 — 마지막 완료 노드 다음부터 재개하거나, 부작용 노드를 지났으면 실패로 확정한다.

**독립 선행 가능 항목**: 스케줄러 중복 발화 방지만은 지금 당장 DB advisory lock으로 넣을 수 있다. 다중 인스턴스 배포를 여는 가장 싼 안전장치다.

### 1.4 (4단계) 재시도 · 에러 분기 · 멱등성

재시도는 기존 자산과 결합한다 — `error_catalog.json`과 NodeError 계약에 **오류 클래스별 재시도 가능 여부**(429·타임아웃·5xx는 지수 백오프, 401·검증 오류는 즉시 실패)를 필드로 추가하고, 노드 설정에는 `retries`·`backoff`·`timeout` 세 개만 노출한다. 에러 분기는 executor가 NodeError를 던지면 엔진이 `error` 출력 핸들로 흐름을 돌리는 것으로 인터프리터에서 구현이 자명하다. 워크플로우 실패 시 지정 워크플로우를 실행하는 에러 트리거(n8n Error Trigger 상당)를 얹으면 "실패하면 알림" 패턴이 사용자 손에 들어간다.

멱등성은 재시도와 **반드시 동시에** 들어간다. 재시도가 생기는 순간 이메일 중복 발송이 실제로 발생한다. 두 겹: (1) 트리거 중복 방지 — `idempotency_key`(웹훅 payload 해시, RSS 항목 id)에 unique 제약, (2) 부작용 노드 중복 방지 — 이메일·슬랙·카카오 executor는 `(run_id, node_id)` 전송 기록을 확인해 성공분을 건너뛴다. RSS cursor의 SEEN_WINDOW 해결과 같은 종류의 사고방식이다.

## 2. 앱 빌더 개선 — 5축

현 구조 진단: 앱 빌더는 UI 컴포넌트 17종 + 블루프린트 로직 노드(trigger/value/action/workflowNode)의 자체 편집기·자체 생성 에이전트를 갖고, 워크플로우와의 접점은 `workflowNode`의 `projectId` 참조 한 줄이다. 실행 결과는 `run_workflow`의 문자열 하나(`result_text`)로 받는다. "따로 논다"와 "빈약하다"의 원인이 이 두 지점이다.

### 2.1 워크플로우 → 앱 원클릭 (최우선)

캔버스에 "앱으로 배포" 버튼을 두고, 워크플로우가 요구하는 사용자 입력을 스캔해 입력 폼을 자동 생성한다. 이는 T1 문제(`community_sanitize.needs_input_for`가 credential·secret·path만 보는 한계)와 같은 뿌리다 — 노드 정의에 "사용자 제공 필드" 선언 스키마를 한 번 만들면 **템플릿 설치 폼과 앱 입력 폼이 같은 것에서 파생**된다. 두 과제를 한 스키마로 닫는다.

### 2.2 구조화된 출력 바인딩

워크플로우의 특정 노드 출력을 특정 컴포넌트에 바인딩한다 — jsonParser 출력 배열 → table, imageGeneration → image, HWPX 산출물 → 다운로드 버튼. 캔버스의 `FieldBindingPicker` UX 문법을 확장하고, 백엔드는 §1.2 run_steps가 노드별 출력에 주소를 부여하면서 공짜로 생긴다. 실행 진행 표시(빈 화면 대기 해소)도 같은 기반이다.

### 2.3 채팅 컴포넌트 — 배포형 챗봇

로드맵 26번이 이미 "배포된 챗봇" 을 목표로 적고 있으나 앱 빌더에 채팅 UI가 없다. llmNode의 세션 메모리(NodeMemory)가 있으므로 채팅 컴포넌트 + 세션 유지 + 워크플로우 호출만 이으면 되고, 26번 착수 전에도 LLM 노드 단독 봇이 나온다.

### 2.4 앱 수준 데이터 — 제출 이력과 저장소

현재 앱은 상태 없는 함수다. 최소 버전으로 앱별 제출 이력(누가 언제 무슨 입력, 결과)을 table 컴포넌트에 바인딩 가능하게 한다. usage_tracking에 이미 기록이 남으므로 제작자용 뷰부터 시작할 수 있다. 신청 접수·설문·요청 큐 류의 실무 앱이 열린다.

### 2.5 배포 다듬기 — 버전 고정, 접근 제어, 임베드

편집 중 버전과 배포 버전을 분리한다: **배포 = 특정 ProjectRevision 고정**, 롤백은 이전 릴리스 재지정. 그 외 share 링크 비밀번호/워크스페이스 한정, 앱별 실행 quota(부스 체험에서도 즉시 필요), iframe 임베드.

## 4. 시연회 준비 — 부스 형식

### 4.1 체험 동선 2층 구조

**층 1 (모든 방문자, 폰, 1~2분)**: 부스 앞 QR → 배포 앱 → 입력 한 번에 결과. 결과가 방문자에게 남는 것이 핵심(HWPX 다운로드 또는 이메일 발송). 후보: (a) 키워드 → 네이버 뉴스 요약 HWPX(한국형 정체성 최대), (b) 주소 → 도로명주소 정제(3초 완결, 승인키 전제), (c) 텍스트 → 포스터 생성(시각 임팩트). 업무 관련 청중이면 a, 유동 인구형 행사면 b/c.

**층 2 (관심 방문자, 태블릿, 5분)**: "어떻게 만든 거예요?"에만 캔버스 공개. 방문자가 자기 업무를 한 문장으로 말하게 하고 자연어 생성 → 그래프가 나타나는 장면이 최강 전환 지점. 생성 품질 리스크는 dry-run을 "실행 전 검증"으로 어필해 흡수.

**승인 연출**: 층 1 앱에 승인 단계를 넣고 부스 모니터에 승인 대기 큐 실시간 표시. 운영자가 승인할 때마다 방문자 폰에 결과 도착 — 거버넌스 메시지 + 사회적 증거.

### 4.2 이번 주 체크리스트

## 5. 브라우저 자동화 방침 (Playwright 질의 관련)

n8n에는 공식 Playwright 노드가 없고 커뮤니티 노드 여럿(n8n-nodes-playwright 등)이 있으나, 브라우저 바이너리 ~1GB·Docker 의존성 문제가 공통이다. 실무에서 더 쓰이는 것은 **Browserless 패턴** — 브라우저를 별도 Docker 서비스로 띄우고 원격 명령만 보내는 구조.

본 프로젝트가 `webCrawlerNode`를 JS 렌더링(SPA·동적 페이지)으로 확장한다면 **프로세스 내장이 아니라 Browserless 패턴을 채택한다.** 근거: (1) 단일 프로세스 구조에서 Chromium의 메모리·크래시가 API 서버 전체로 번진다, (2) `url_guard`(SSRF 방어)를 브라우저가 우회하는 새 구멍이 생기므로 격리 경계에서 URL 검증을 재적용해야 한다, (3) 격리 컨테이너 인프라는 §1.1의 pythonNode 격리(Task Runner 패턴)와 공유된다.

## 맺음말

과제가 많아 보이지만 설계 결정이 필요한 지점은 셋뿐이다 — 디스패처 전환, Run/Step 모델, 사용자 제공 필드 스키마. 나머지는 이 셋의 파생이며, 참조 프레임워크들이 이미 검증한 설계를 이식하면 시행착오 비용을 건너뛸 수 있다. 시연회까지는 안정화에 집중하고, 부스에서 얻은 관측으로 32·33번의 내부 순서를 확정하는 것을 권한다.
