## 요약

이 프로젝트는 "파일럿"이라는 이름과 달리 이미 상당히 넓은 표면적을 갖고 있다. 노드 정의 28종(한국형 서비스 포함), LLM 기반 워크플로우 자동 생성, dry-run, 프로젝트 리비전과 diff/복원, 휴먼 승인(Human-in-the-loop), 커뮤니티 템플릿 242종, App Builder와 공개 배포, 자격증명 AES-256-GCM 암호화, 관리자 콘솔, 사용량 추적, Langfuse 연동까지 — n8n이나 Make의 핵심 축을 대부분 흉내 내고 있고, HWPX·네이버·도로명주소·공공데이터포털 같은 한국형 노드는 오히려 두 제품에 없는 차별점이다.

반면 두 가지 축에서 격차가 뚜렷하다. 첫째, **실행 엔진의 흐름 제어와 데이터 조작 프리미티브**(루프, 병합, 다중 분기, 서브워크플로우, 노드별 재시도/에러 분기, 범용 웹훅 트리거)가 빠져 있어 만들 수 있는 워크플로우의 형태 자체가 순차·단일 분기에 갇혀 있다. 둘째, **프로덕션 아키텍처**가 단일 FastAPI 프로세스 + 인프로세스 APScheduler 구조라서, 서버 재시작 한 번에 실행 중인 워크플로우와 예약 작업이 유실될 수 있고, 자체 보안 평가서에도 `graph.py`의 `exec()` 기반 실행이 미해결로 남아 있다. 아래에서 이 둘을 우선순위와 함께 정리한다.

## 2. 추가할 만한 기능 (우선순위순)

### 2.1 흐름 제어 프리미티브 — 가장 값이 큰 갭

노드 정의를 확인한 결과 분기는 `conditionNode` 하나뿐이고 루프·병합·서브워크플로우가 없다. 이건 개별 커넥터 부족과는 성격이 다른 문제다. 커넥터가 없으면 특정 서비스를 못 붙일 뿐이지만, 루프가 없으면 "RSS에서 새 글 N개를 받아 각각 요약해 슬랙에 보낸다" 같은 가장 흔한 자동화 패턴을 표현할 수 없다. 커뮤니티 템플릿 142종을 n8n에서 옮겨왔다고 되어 있는데, n8n 템플릿 상당수가 Loop/Merge/Switch에 의존하므로 이 프리미티브가 없으면 이식 가능한 템플릿의 상한도 함께 낮아진다. 구체적으로는 배열 항목을 순회하는 반복 노드(Make의 Iterator, n8n의 Loop Over Items), 여러 분기의 결과를 합치는 병합 노드(Make의 Aggregator), 다중 분기 스위치, 그리고 워크플로우를 다른 워크플로우에서 호출하는 서브워크플로우 노드 순으로 도입을 권한다. 서브워크플로우는 커뮤니티 템플릿을 "부품"으로 재사용하게 해 주므로 이미 갖춘 템플릿 자산과 시너지가 크다.

### 2.2 범용 웹훅 트리거

트리거가 schedule과 앱별 4종(Gmail·RSS·YouTube·네이버)뿐이다. 라우트에 `/api/webhooks`가 있지만 승인 콜백 용도로 보이고, 사용자가 임의의 외부 시스템에서 워크플로우를 호출할 수 있는 범용 인바운드 웹훅 노드는 없다. n8n과 Make 모두에서 웹훅은 사용 빈도 1~2위의 트리거이고, 이것이 있어야 사내 시스템·폼 빌더·타 SaaS와의 연동이 커넥터 개발 없이 열린다. 이미 `url_guard`(SSRF 방어)와 App Builder의 공개 실행 엔드포인트(`/api/apps/{share_token}/execute`)가 있으므로, 서명 검증(HMAC)과 사용자별 rate limit만 얹으면 기존 인프라 위에서 비교적 저렴하게 구현할 수 있다.

### 2.3 노드별 재시도·타임아웃·에러 분기

`graph.py`에서 재시도 로직이 확인되지 않는다. 오류 카탈로그와 NodeError 계약이라는 좋은 기반은 이미 있으니, 그 위에 (1) 노드 설정으로 재시도 횟수·백오프·타임아웃 지정, (2) 노드에 성공/실패 두 출력 핸들을 두는 에러 분기, (3) 워크플로우 실패 시 별도 워크플로우를 실행하는 에러 트리거(n8n의 Error Trigger 상당)를 얹는 것을 권한다. 특히 이 프로젝트는 외부 API(Gemini, 네이버, 공공데이터포털) 의존이 크므로 일시적 장애를 노드 수준에서 흡수하는 능력이 실사용 만족도를 직접 좌우한다.

### 2.4 편집기 반복 개발 경험 — 부분 실행과 데이터 고정

dry-run과 mock 시나리오는 이미 훌륭하다. 여기에 n8n의 두 기능을 더하면 편집 루프가 완성된다. 하나는 특정 노드까지만 실행하거나 특정 노드 하나만 재실행하는 부분 실행이고, 다른 하나는 이전 실행의 출력을 노드에 "고정(pin)"해 두고 하류 노드를 개발할 때 상류 API를 반복 호출하지 않게 하는 데이터 피닝이다. LLM·외부 API 호출 비용을 추적하는 usage_tracking이 이미 있는 만큼, 피닝은 사용자 비용 절감 기능으로도 소구할 수 있다.

### 2.5 AI 에이전트 노드와 MCP

현재 LLM 노드는 단일 호출형이고, 에이전트적 능력(도구 선택·다단계 추론)은 워크플로우 "생성" 쪽 메타 에이전트에만 있다. 2026년 두 경쟁 제품의 공통 방향은 이것을 "실행" 쪽으로 가져오는 것이다 — n8n은 AI 도구·메모리·LLM 호출을 별도 서브워크플로우 없이 일반 워크플로우 안의 노드 타입으로 쓸 수 있게 했고, Make는 에이전트를 시나리오와 같은 캔버스에서 구성하고 Reasoning 패널로 판단 과정을 보여준다. 이 프로젝트에는 이미 humanApprovalNode와 평가 시스템이 있으므로, "다른 노드들을 도구로 쓰는 에이전트 노드 + 파괴적 도구는 승인 노드 강제"라는 조합은 자연스럽고, 로드맵 28번(시맨틱 포인팅)이 막힌 지점(범위 안 파괴적 동작)과도 같은 해법(도구 제한·diff preview)을 공유한다. MCP 클라이언트 노드는 커넥터를 직접 만들지 않고도 외부 도구 생태계를 통째로 흡수하는 지렛대라서, 커넥터 수 격차(28종 vs 수천 개)를 좁히는 현실적인 경로다.

### 2.6 데이터 조작 노드 소형 3종

jsonParserNode와 formatNode는 있으나, 필드 몇 개를 꺼내 이름을 바꾸고 기본값을 채우는 Set/Edit Fields, 중복 제거(dedupe), 정렬/필터 같은 소형 변환 노드가 없어서 그 역할이 전부 제한형 pythonNode나 LLM 노드로 쏠릴 것이다. LLM으로 데이터 변환을 대신하면 비용·비결정성 문제가 생기므로, 결정적 변환 노드를 갖추는 것이 품질과 비용 양쪽에 이득이다.

### 2.7 거버넌스 시각화 (중장기)

Make Grid는 "이 필드를 바꾸면 뭐가 깨지는가"를 도구 경계를 넘어 하나의 의존성 맵으로 답하는 기능으로, Make가 가장 강하게 미는 차별점이다. 이 프로젝트도 워크플로우·자격증명·스케줄·배포 앱·템플릿이라는 자원 그래프가 이미 DB에 있으므로, 자격증명 삭제나 노드 정의 변경 시 영향받는 워크플로우 목록을 보여주는 축소판부터 시작할 수 있다. Workspace/RBAC(백로그 11번)이 끝나 조직 단위 사용이 시작되면 필요성이 급격히 커지는 기능이다.

## 3. 프로덕션 레벨 전환에 필요한 것

기능 추가보다 먼저 처리해야 할 것들이다. 자체 문서(`security_assessment.md`, 런북)에 이미 절반쯤 진단되어 있으므로, 여기서는 남은 항목과 문서에 없는 항목을 중심으로 적는다.

### 3.1 실행 코드 생성 → 디스패처 전환 (자체 보고서상 미해결, 최우선)

보안 평가서가 스스로 명시하듯 `graph.py`는 워크플로우를 파이썬 소스로 변환한 뒤 `exec()`로 실행하며, AST 검사로 완화만 되어 있고 근본 해결(각 노드 실행 함수를 직접 호출하는 dispatcher 구조)은 남아 있다. 이 전환은 보안 문제인 동시에 2장의 기능들(노드별 재시도, 에러 분기, 부분 실행, 실행 상태 영속화)의 전제 조건이기도 하다 — 코드 생성 방식으로는 노드 단위 수명주기에 개입할 지점이 없기 때문이다. 참고로 n8n 2.0도 같은 이유로 Task Runner를 도입해 워크플로우 실행을 격리했고, 이것이 임의 코드 실행 위험을 줄이는 핵심 변경이었다. 전환 전까지는 런북에 계획된 무권한 계정 + systemd hardening(현재 미적용으로 기록됨)이라도 먼저 적용해야 한다.

### 3.2 실행의 내구성 — 큐 기반 워커 분리

현재 구조는 uvicorn 단일 프로세스가 API 서빙·워크플로우 실행·APScheduler 스케줄링을 전부 겸한다(requirements와 코드에서 Celery/Redis/RQ 부재 확인). 이 구조의 문제는 세 가지다. 배포나 크래시로 프로세스가 죽으면 실행 중이던 워크플로우가 흔적 없이 사라지고, LLM 호출처럼 수십 초 걸리는 실행이 이벤트 루프와 자원을 점유해 API 응답성이 흔들리며, 수평 확장이 불가능하다(스케줄러가 인프로세스라 인스턴스를 2개 띄우면 cron이 중복 발화한다). 권장 경로는 실행 요청을 DB 또는 Redis 큐에 적재하고 별도 워커 프로세스가 소비하는 구조로, 실행 상태(대기/진행/노드별 완료)를 DB에 기록해 워커 재시작 시 재개하거나 최소한 "실패로 확정"할 수 있게 만드는 것이다. n8n이 Redis 기반 큐 모드로 병렬 실행을 처리하는 구성이 그대로 참고가 된다. 스케줄러는 워커 중 리더 하나만 돌리거나 DB 락으로 중복 발화를 막는다.

### 3.3 멱등성과 트리거 신뢰성

RSS 트리거의 cursor 겹침 창 문제를 이미 훌륭하게 해결한 기록이 있는데, 같은 원칙을 실행 쪽에도 적용해야 한다. 웹훅/트리거 재전송이나 워커 재시도로 같은 실행이 두 번 돌 때 이메일이 두 번 나가지 않도록, 실행 단위 idempotency key와 부작용 노드(이메일·슬랙·DB 쓰기)의 전송 기록 대조가 필요하다. 특히 3.2의 재시도 인프라를 넣는 순간 이 문제가 실제로 발생하기 시작하므로 함께 설계해야 한다.

### 3.4 운영 가시성

Langfuse는 LLM 호출만 본다. 프로덕션에는 그 바깥이 필요하다: 예외 수집(Sentry 계열), 프로세스·큐 깊이·실행 지연 메트릭(Prometheus + Grafana 또는 관리형 APM), 구조화 로깅과 실행 ID 상관관계, 그리고 헬스체크 엔드포인트(스케줄러 생존·DB 연결·큐 적체 포함). 관리자 통계 화면이 이미 있으므로 "지난 5분간 실패율이 임계치를 넘으면 운영자에게 알림" 같은 얼럿을 기존 텔레그램 봇 인프라에 연결하면 저렴하게 시작할 수 있다.

### 3.5 배포·환경 체계

레포에 docker-compose는 Langfuse용만 있고 앱 자체의 컨테이너화·CI 파이프라인이 보이지 않는다. 최소 구성으로 (1) backend/frontend Dockerfile과 compose(또는 단일 VM이면 systemd 유닛), (2) 테스트가 이미 풍부하므로(test_ 파일 다수, 템플릿 회귀 508건) GitHub Actions에서 push마다 실행, (3) staging 환경 분리와 마이그레이션 자동 적용(alembic 체계는 이미 0021까지 있음), (4) PostgreSQL 정기 백업과 복구 리허설 — 특히 자격증명이 암호화되어 있으므로 `CREDENTIAL_ENCRYPTION_KEY` 유실 = 전체 자격증명 유실이라는 점에서 키를 secret manager에 별도 보관하고 백업 정책에 명시해야 한다(보안 평가서에도 경고가 있다).

### 3.6 남은 보안 항목

보안 평가서에서 완료로 표시되지 않은 것들: 업로드 엔드포인트가 비로그인 허용이므로 Nginx rate limit + IP/사용자별 quota + 만료 파일 정리, OS 권한 격리 런북 적용, 그리고 문서에 없는 항목으로 API 전반의 rate limiting(현재 확인되지 않음)과 워크플로우 실행의 자원 상한(노드 수 제한은 있으나 실행 시간·메모리 상한 명시 필요)을 추가한다. 커뮤니티 템플릿·앱 공개 배포가 이미 열려 있는 서비스이므로, 검토 대기 79건의 승인 주체 지정(로드맵이 지적한 미결 사항)도 신뢰·안전 관점에서 운영 이슈다.

### 3.7 조직 사용의 전제 — RBAC 완주

로드맵이 정확히 짚었듯 자격증명이 소유자 개인에 묶여 있어 소유자가 나가면 워크플로우가 멈춘다. TEAM-2(workspace 자격증명)·TEAM-3은 프로덕션에서 "팀이 쓰는 도구"가 되기 위한 전제이므로, 신규 기능보다 앞에 두는 현재 로드맵 순서가 타당하다.

## 5. 맺음말

n8n·Make와 정면으로 커넥터 수를 겨루는 것은 승산이 없는 게임이고, 이 프로젝트의 강점은 이미 다른 곳에 있다 — 한국형 서비스 노드(HWPX·네이버·공공데이터), LLM 생성 + 평가 + 승인이 결합된 파이프라인, 그리고 App Builder를 통한 배포다. 따라서 커넥터 확장보다는 (1) 실행 엔진을 프로덕션급으로 올리고, (2) 흐름 제어 프리미티브로 표현력의 상한을 걷어낸 뒤, (3) MCP로 커넥터 격차를 우회하는 순서가 자원 대비 효과가 가장 크다고 판단된다. 자체 문서화 수준(결함 추적, 사후 검증 기록)이 이미 높아서, 위 항목 대부분은 새 진단이 아니라 기존 로드맵의 우선순위 재배열에 가깝다는 점도 긍정적이다.
