## 1. 결론

현재 각각 1차 메뉴로 노출된 `웹훅 관리`, `봇 관리`, `스케줄 관리`는 **운영**으로 묶는다.
`API 센터`는 **설정 > API 센터**, `커뮤니티 템플릿`은 **커뮤니티 > 템플릿**으로 이동한다.

사이드바에서 하위 메뉴를 펼치는 아코디언 방식은 사용하지 않는다. 데스크톱 축소 상태와 모바일
드로어에서 위계가 불안정해지기 때문이다. 사이드바에는 1차 목적지만 표시하고, 각 섹션에 진입한
후 페이지 상단의 보조 내비게이션으로 하위 페이지를 이동한다.

추천 1차 메뉴는 다음과 같다.

```text
제작
  홈
  내 워크플로우
  앱 빌더 (AI)
  튜토리얼

관리 및 탐색
  운영
  커뮤니티
  통계

계정 및 도움말
  설정
  패치 노트
  서비스 소개
```

관리자 패널은 기존처럼 관리자에게만 하단에 노출한다.

## 2. 메뉴 이동표

| 현재 메뉴/경로 | 목표 위치 | 권장 경로 | 비고 |
| --- | --- | --- | --- |
| 웹훅 관리 `/webhooks` | 운영 > 웹훅 | `/operations/webhooks` | 기존 URL은 리다이렉트 |
| 봇 관리 `/bots` | 운영 > 봇 | `/operations/bots` | Discord와 Telegram을 동일 섹션에서 관리 |
| 스케줄 관리 `/scheduler` | 운영 > 스케줄 | `/operations/schedules` | 복수형 경로로 통일 |
| API 센터 `/apicenter` | 설정 > API 센터 | `/settings/api-center` | 실행 오류에서 직접 진입 가능한 URL 유지 |
| 커뮤니티 템플릿 `/templates` | 커뮤니티 > 템플릿 | `/community/templates` | 기존 URL은 리다이렉트 |
| 설정 `/settings` | 설정 > 프로필 | `/settings/profile` | 설정의 기존 탭도 URL을 갖도록 전환 |

기존 URL은 최소 한 번의 안정화 기간 동안 `replace` 방식으로 새 URL에 연결한다. 쿼리와
해시가 있을 경우 그대로 전달하여 저장된 링크와 오류 해결 링크가 깨지지 않게 한다.

## 3. 섹션별 화면 설계

### 3.1 운영

운영은 “이미 만들어진 자동화가 언제, 어디에서 실행되고 있는가”를 확인하는 공간으로 정의한다.
제작 기능과 구분되므로 `자동화`보다 `운영`이라는 명칭이 현재 기능에 더 정확하다.

보조 내비게이션:

```text
개요 | 웹훅 | 봇 | 스케줄
```

- **개요**: 활성 웹훅·봇·스케줄 수, 최근 실행, 주의가 필요한 연결을 요약한다.
- **웹훅**: 기존 웹훅 목록, URL 복사, 활성화, 수신 로그와 삭제 기능을 이전한다.
- **봇**: 봇 상태, 실행/정지, 최근 로그와 연결된 워크플로우를 표시한다.
- **스케줄**: 실행 주기, 다음 실행 시각, 활성 상태와 연결된 워크플로우를 표시한다.
- 각 항목에는 해당 워크플로우를 여는 공통 동작을 제공한다.
- 문제가 있는 항목만 운영 메뉴에 배지로 집계한다. 전체 항목 수는 상시 배지로 표시하지 않는다.

초기 버전의 개요는 세 API의 결과를 합산한 읽기 전용 화면으로 시작한다. 통합 백엔드 API는
화면 요구가 안정된 뒤 도입하여 과도한 선행 작업을 피한다.

### 3.2 설정과 API 센터

설정의 현재 `useState` 탭을 URL 기반 하위 페이지로 전환한다.

```text
프로필 | 친구 | 화면 | 사용량 표시 | 데이터 | API 센터
```

- API 센터의 기능과 자격 증명 저장 방식은 변경하지 않고 위치와 화면 셸만 이전한다.
- 명칭은 당분간 `API 센터`를 유지한다. `연동`으로만 바꾸면 봇·웹훅 관리와 혼동될 수 있다.
- 노드 설정이나 인증 오류의 “API 센터에서 연결” 버튼은 `/settings/api-center?provider=google`
  같은 직접 링크를 사용한다.
- `provider` 쿼리가 있으면 해당 공급자 카드를 강조하고 화면 안으로 스크롤한다.
- 자격 증명 원문은 기존 원칙대로 그래프, revision, 템플릿과 로그에 포함하지 않는다.

API 센터는 설정 하위가 적절하지만, 사용자가 실행 오류를 해결하는 핵심 경로이므로 사이드바에서
사라진 뒤에도 노드 Inspector와 오류 메시지의 문맥형 바로가기는 강화해야 한다.

### 3.3 커뮤니티와 템플릿

보조 내비게이션은 기능 출시 단계에 따라 점진적으로 확장한다.

```text
현재:  템플릿
향후:  둘러보기 | 템플릿 | 제작자 | 커뮤니티 노드
```

- 첫 단계에서는 `커뮤니티` 1차 메뉴가 `/community/templates`로 바로 이동한다.
- 아직 제공하지 않는 둘러보기·제작자·커뮤니티 노드는 메뉴에 비활성 항목으로 미리 노출하지 않는다.
- 템플릿은 로드맵 순서대로 버전 발행, fork 계보, credential/file/secret 제거, 신고와 검수 기능을
  갖춘 뒤 커뮤니티 홈의 주요 콘텐츠가 된다.
- 선언형 커뮤니티 노드는 템플릿과 같은 화면에 섞지 않고 별도 하위 페이지로 추가한다.
- 실행형 커뮤니티 노드는 격리·서명·quota 기반이 마련되기 전까지 내비게이션 계획에 포함하지 않는다.

## 4. 권장 프론트엔드 구조

```text
App
├─ MainSidebar
├─ OperationsLayout
│  ├─ OperationsOverviewPage
│  ├─ WebhookManagerPage
│  ├─ BotManagerPage
│  └─ SchedulerPage
├─ CommunityLayout
│  └─ TemplatesPage
└─ SettingsLayout
   ├─ ProfileSettingsPage
   ├─ FriendsSettingsPage
   ├─ AppearanceSettingsPage
   ├─ UsageDisplaySettingsPage
   ├─ DataSettingsPage
   └─ ApiCenterPage
```

공통 `SectionLayout`은 제목, 설명, 보조 내비게이션, 모바일 가로 스크롤, breadcrumb 영역만
담는다. 각 관리 페이지의 데이터 요청과 동작은 그대로 유지해 정보 구조 변경과 기능 변경을 분리한다.

사이드바 항목은 JSX에 반복해서 작성하지 않고 하나의 내비게이션 설정으로 관리한다.

```text
id, label, icon, href, activeMatch, group, auth, adminOnly
```

데스크톱·모바일 사이드바가 같은 설정을 사용해야 메뉴 누락과 활성 상태 불일치를 방지할 수 있다.

## 5. 구현 단계

### 단계 1. 라우트와 공통 셸 준비

1. `SectionLayout`과 `SectionNav`를 추가한다.
2. `/operations/*`, `/community/*`, `/settings/*` 중첩 라우트를 정의한다.
3. 기존 URL용 호환 리다이렉트를 추가한다.
4. 새 URL에서 새로고침·뒤로가기·직접 접속이 가능한지 먼저 검증한다.

완료 기준: 기존 링크가 깨지지 않고, 모든 하위 페이지가 고유 URL과 올바른 활성 상태를 가진다.

### 단계 2. 운영 통합

1. 기존 세 관리 페이지를 `OperationsLayout` 아래로 이동한다.
2. API와 페이지 내부 로직을 바꾸지 않은 채 보조 내비게이션만 공통화한다.
3. 읽기 전용 운영 개요와 오류/정지 상태 요약을 추가한다.
4. 빈 상태의 행동을 “에디터에서 트리거 추가”와 “연결된 워크플로우 열기”로 통일한다.

완료 기준: 사용자가 운영 진입 후 한 번의 클릭으로 웹훅·봇·스케줄 사이를 이동할 수 있다.

### 단계 3. 설정과 API 센터 통합

1. 현재 설정 탭을 하위 라우트 단위 컴포넌트로 분리한다.
2. `ApiCenterPage`를 설정 셸 안으로 이동한다.
3. provider 직접 링크, 포커스와 스크롤 동작을 추가한다.
4. `/apicenter` 및 기존 오류 안내 링크를 새 경로로 연결한다.

완료 기준: API 인증 오류에서 필요한 공급자까지 두 번 이하의 동작으로 도달한다.

### 단계 4. 커뮤니티 셸 도입

1. `CommunityLayout`을 만들고 기존 템플릿 페이지를 하위에 배치한다.
2. `/templates` 호환 리다이렉트를 추가한다.
3. 발행 주체, 검수 상태와 credential 요구 사항을 향후 표시할 수 있도록 카드 경계를 정리한다.
4. 로드맵의 Versioned Community Template 구현 시 둘러보기와 발행 관리 화면을 추가한다.

완료 기준: 템플릿 기능을 유지하면서 향후 커뮤니티 페이지가 추가되어도 1차 사이드바가 늘어나지 않는다.

### 단계 5. 사이드바 단순화와 출시

1. 웹훅·봇·스케줄·API 센터·커뮤니티 템플릿 개별 항목을 제거한다.
2. `운영`, `커뮤니티`, `설정`의 상위 경로 전체를 활성 범위로 처리한다.
3. 축소 사이드바 tooltip, 모바일 닫힘 동작과 키보드 탐색을 검증한다.
4. 이전·이후 메뉴 클릭률과 목적 페이지 도달 시간을 비교한 뒤 명칭을 확정한다.

완료 기준: 1차 일반 사용자 메뉴가 기존 13개에서 10개로 줄고, 모바일에서도 하위 페이지 접근이
두 단계 이내로 유지된다.

## 6. 검증 항목

- 기존 5개 URL에서 새 위치로 정상 이동하고 로그인 복귀 후 목적지가 보존되는가
- 새로고침, 뒤로가기와 앞으로가기가 내부 탭 상태와 일치하는가
- `/operations/*`, `/community/*`, `/settings/*`에서 올바른 1차 메뉴가 활성화되는가
- 축소·모바일 사이드바에서 텍스트 없이도 tooltip과 접근 가능한 이름이 제공되는가
- 키보드만으로 1차 메뉴와 보조 내비게이션을 이동할 수 있는가
- API Center provider 직접 링크가 정확한 카드를 열고 강조하는가
- 기존 웹훅·봇·스케줄의 생성, 활성화, 로그, 삭제 기능에 회귀가 없는가
- 라이트·다크 테마와 좁은 화면에서 보조 내비게이션이 잘리거나 두 줄로 무너지지 않는가

측정 이벤트는 `sidebar_section_opened`, `section_tab_opened`, `legacy_route_redirected`,
`credential_context_link_opened` 정도로 제한한다. 개편 전후에 메뉴 클릭 수가 줄어도 목적 페이지 도달률과
작업 완료율이 높아지는지를 우선 판단한다.

## 6.5 구현 기록 (2026-08-28)

단계 1~5를 적용했다. 회귀를 줄이기 위해 기존 페이지 컴포넌트의 내부 로직은 바꾸지 않고
경로·셸·내비게이션만 옮겼다(§4의 원칙 그대로).

- **라우트**: `/operations`(개요)·`/operations/webhooks|bots|schedules`,
  `/community/templates`, `/settings/:tab`(profile/friends/appearance/tokens/privacy),
  `/settings/api-center`. 구 URL 5종(`/webhooks`, `/bots`, `/scheduler`, `/apicenter`,
  `/templates`)과 `/settings`는 쿼리·해시를 보존하는 replace 리다이렉트로 연결했다.
- **보조 내비게이션**: `SectionTabs` + `navigation.js`(탭 정의 정본). 운영 4페이지와
  설정 6페이지 상단에 같은 탭이 붙는다. 설정 페이지의 내부 탭은 URL 기반으로 전환했다.
- **운영 개요**: 세 API(웹훅/봇/스케줄)를 합산하는 읽기 전용 화면(`OperationsOverviewPage`).
  불러오기에 실패한 축은 0으로 속이지 않고 '확인 불가'로 표시한다.
- **사이드바**: JSX 반복 대신 `NAV_GROUPS` 설정 하나로 렌더링(§4). 그룹 캡션
  제작/관리 및 탐색/계정 및 도움말 표시. 일반 메뉴 13개 → 11개(계획 10개 + 신설 승인 대기함).
- **API 센터 딥링크**: `/settings/api-center?provider=<id>`가 해당 공급자 카드를 강조하고
  스크롤한다(§3.2).
- **부수 정리**: 학습 센터의 '홈으로' 버튼 제거(사이드바가 대신함), 카탈로그 히어로를
  문서 페이지와 같은 위계(eyebrow → 큰 제목 → 부제 → 구분선)로 통일.

미적용으로 남긴 것: 운영 메뉴의 문제-항목 배지(백엔드 상태 신호 필요), 측정 이벤트 4종
(분석 수집 기반 없음), 명칭 확정(단계 5-4 — 사용 데이터 필요), 커뮤니티 향후 탭
(계획대로 기능 출시 전 미노출).

## 7. 이번 개편에서 제외할 범위

- 웹훅·봇·스케줄 백엔드 모델 통합
- API 자격 증명 저장 방식 변경
