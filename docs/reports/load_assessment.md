# 시스템 부하 및 동시 사용자 처리 능력 분석

본 문서는 현재 시스템 아키텍처 및 서버 스펙을 기준으로 최대 동시 접속자 수 및 시스템 병목 구간을 계산한 결과입니다.

## 1. 서버 인프라 및 스펙
- **CPU**: 2 vCPU
- **Memory**: 2GB (실제 가용 메모리 약 500MB 수준)
- **Swap**: 2GB
- **Web Server**: Nginx (리버스 프록시 및 정적 리소스 서빙)
- **Backend**: FastAPI + Uvicorn (워커 1개로 동작)
- **Database**: PostgreSQL (SQLAlchemy 기본 설정 사용)

## 2. 구간별 동시 처리 능력 추정

### 1) 프론트엔드 (UI 렌더링 및 정적 리소스)
- **처리 방식**: Nginx를 통해 정적으로 빌드된 React 앱 서빙
- **동시 처리량**: 수백 ~ 수천 명
- **평가**: 매우 안정적. 단순히 화면을 띄워두거나 메뉴를 이동하는 데에는 전혀 문제가 없습니다.

### 2) 백엔드 기본 API (단순 조회/저장)
- **처리 방식**: FastAPI 워커 1개, 비동기 I/O
- **동시 처리량**: 약 50 ~ 100 RPS (초당 요청 수)
- **평가**: 데이터베이스의 단순 쿼리는 매우 빠르므로, 로그인이나 목록 조회 같은 동작은 원활히 처리됩니다.

### 3) ⚠️ 핵심 병목: AI 앱 및 워크플로우 생성 (LLM 호출)
- **문제점**:
  - `generate_app` 등 생성 API는 호출 시 OpenAI API 응답 대기로 인해 약 **10초 ~ 30초**가 소요됩니다.
  - 현재 `Depends(get_db)` 방식으로 인해, **API 응답이 완료될 때까지 하나의 요청이 DB 커넥션 1개를 독점(Lock)하게 됩니다.**
- **DB Connection Pool 한계**:
  - 기본 설정(`pool_size`=5, `max_overflow`=10)에 따라 **최대 동시 연결 수는 15개**입니다.
- **최대 동시 접속 수**:
  - 동시에 15명이 "생성" 버튼을 누르면 풀이 가득 찹니다.
  - **16번째 사용자**부터는 DB 연결을 얻지 못해 무한 대기 상태에 빠지거나 `TimeoutError`가 발생합니다.
- **FastAPI Worker 한계**:
  - Uvicorn 워커가 1개(`--workers 1`)이므로, 이벤트 루프나 쓰레드 풀(40개 제한) 병목이 발생할 수 있습니다.

## 3. 권장 해결 방안 (전시회용 임시 조치)
1. **DB 커넥션 풀 강제 증가**: `database.py`에서 `pool_size=20`, `max_overflow=50` 등으로 상향 조정 (약 70명 동시 생성 가능).
2. **FastAPI 워커 수 조정**: 2GB RAM 한도 내에서 `uvicorn` 워커를 2~3개로 증가.
3. **코드 리팩토링 (가장 권장)**: LLM API 호출 전후로만 DB 트랜잭션을 묶고, 대기 시간 중에는 DB 커넥션을 반환하도록 세션 스코프를 분리해야 합니다.
