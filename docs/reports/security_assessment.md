# 보안 취약점 점검 및 평가 보고서

본 문서는 현재 시스템의 내부 코드 구조와 엔드포인트를 기반으로 식별된 보안 취약점 목록입니다.

## 조치 현황 (2026-08-24)

| 항목 | 상태 | 적용 내용 |
| --- | --- | --- |
| 원격 코드 실행 | 부분 완화 | 노드/엣지 구조 검증, 제한형 `pythonNode` AST 허용 목록, 생성 코드 위험 호출 검사를 추가했습니다. |
| OS 권한 격리 | 계획 수립, 미적용 | 전용 무권한 계정과 systemd hardening 적용 절차를 별도 런북으로 작성했습니다. |
| 파일 업로드 | 1차 조치 완료 | 확장자 화이트리스트, 파일당 크기 및 파일 수 제한, UUID 저장명, 부분 파일 정리를 적용했습니다. 문서 컨텍스트 업로드에는 인증과 프로젝트 소유권 검사를 추가했습니다. |
| 민감 정보 평문 저장 | 완료 | API 키와 OAuth 토큰을 AES-256-GCM으로 암호화하고 기존 평문 레코드를 마이그레이션했습니다. |
| 오류 정보 노출 | 완료 | 500 응답에서 내부 예외를 제거하고 검증 오류 응답/로그에서 요청 본문을 제거했습니다. |

운영 환경에서는 `CREDENTIAL_ENCRYPTION_KEY`와 `JWT_SECRET`을 서로 다른 긴 난수로 설정해야 합니다. 업로드 제한은 `MAX_UPLOAD_BYTES`, `MAX_CONTEXT_FILE_BYTES`, `MAX_CONTEXT_FILES`로 조정할 수 있습니다.

권한 탈취 피해를 임시로 제한하는 적용 절차는 [백엔드 임시 권한 격리 실행 계획](./privilege_containment_runbook.md)을 따른다. 해당 계획은 아직 서버에 적용되지 않았다.

## 1. 원격 코드 실행 (RCE) 취약점 (🔴 매우 위험)
- **위치**: `backend/graph.py`
- **문제점**: 워크플로우를 파이썬 코드로 변환한 후, 파이썬 내장 함수인 **`exec()`를 사용하여 서버 메모리 상에서 직접 코드를 실행**합니다. 사용자의 프롬프트를 문자열 치환(`replace`)으로 방어하고 있으나, 복잡한 주입 공격(Injection) 발생 시 우회될 가능성이 있습니다.
- **영향**: 해커가 운영체제 시스템 권한을 탈취하거나, 서버에 저장된 다른 사용자의 모든 데이터를 파괴/유출할 수 있습니다.
- **해결책**:
  1. `exec()`를 제거하고 안전한 AST 파싱 또는 분기문 기반 함수 매핑으로 전환합니다.
  2. 불가피한 경우 컨테이너(Docker 등)를 활용한 샌드박싱 처리가 필수입니다.
- **현재 조치**: `backend/workflow_security.py`에서 안전한 노드 ID와 그래프 참조를 검증하고, `pythonNode`는 데이터 변환에 필요한 AST와 내장 함수/문자열·컬렉션 메서드만 허용합니다. import, 함수/클래스 정의, dunder 접근, 동적 코드 실행은 거부합니다. 생성된 전체 소스도 파싱하여 `eval`, `compile`, `__import__`, 시스템 프로세스 호출 등을 실행 전에 차단합니다.
- **잔여 위험**: `backend/graph.py`의 `exec()` 자체는 아직 남아 있으므로 이 항목은 해결 완료가 아닙니다. 다음 단계에서는 노드 레지스트리가 코드를 생성하지 않고 각 노드 실행 함수를 직접 호출하는 dispatcher 구조로 전환해야 합니다. 전환 전 운영 배포는 최소 권한 사용자와 격리 컨테이너에서 실행해야 합니다.

## 2. 파일 업로드 취약점 (🟠 위험)
- **위치**: `backend/main.py`의 `/api/upload`
- **문제점**: `os.path.basename()`을 통해 디렉터리 경로 조작(Path Traversal) 공격은 잘 차단되어 있습니다. 그러나 **파일 확장자 검사**와 **용량 제한(Size Limit)** 로직이 누락되어 있습니다.
- **영향**:
  - 악의적인 스크립트 파일(.php, .sh 등)이 업로드될 수 있습니다. (다만 Nginx가 정적 서빙만 하므로 직접 실행 위험은 낮음)
  - 공격자가 매우 큰 용량의 더미 파일을 반복 업로드하여 서버 스토리지(2GB)를 고갈시켜, 서비스 전체가 마비되는 DoS 상태에 빠질 수 있습니다.
- **해결책**: `.png`, `.jpg`, `.pdf` 등 허용된 화이트리스트 확장자만 승인하고, 최대 업로드 용량 제한 로직을 추가해야 합니다.
- **현재 조치**: `backend/upload_security.py`에서 서버 생성 UUID 파일명, 확장자 화이트리스트, 스트리밍 용량 제한과 실패 시 부분 파일 삭제를 공통 적용했습니다. RAG 문서는 실제 파서가 지원하는 `.pdf`, `.doc`, `.docx`, `.txt`만 허용하고 최대 파일 수도 제한합니다.
- **잔여 위험**: 공개 배포 앱의 파일 입력을 위해 `/api/upload`는 로그인 없이 사용할 수 있습니다. 운영 단계에서 Nginx 요청 속도 제한, 사용자/IP별 quota, 만료 파일 정리 작업을 추가해야 반복 소용량 업로드에 의한 저장 공간 고갈까지 방어할 수 있습니다.

## 3. 민감 정보 평문 저장 (🟡 경고)
- **위치**: `models.py` 내 `UserApiKey` 테이블
- **문제점**: 사용자의 외부 연동 API 키(OpenAI Key 등)와 카카오 OAuth 토큰 등이 데이터베이스에 평문(Plain text)으로 저장됩니다.
- **영향**: 향후 DB 해킹 사고나 내부자의 악의적 접근 시, 모든 사용자의 API 키가 유출되어 2차적 금전 피해 및 사생활 침해가 발생할 수 있습니다.
- **해결책**: API 키 저장 시 AES-256 등의 강력한 양방향 암호화를 적용하고, 코드 레벨에서 복호화하여 사용해야 합니다.
- **현재 조치**: `backend/credential_crypto.py`에 AES-256-GCM 인증 암호화를 적용했습니다. 저장과 OAuth 갱신 시 암호화하고 실제 외부 API 호출 직전에만 복호화합니다. 기존 평문 필드는 서버 시작 시 암호화하며, 키 식별자를 저장해 현재 전용 키와 기존 `JWT_SECRET` 호환 키를 구분합니다.
- **운영 주의**: 암호화 키를 잃으면 저장된 자격 증명을 복구할 수 없습니다. 키를 소스 저장소에 커밋하지 말고 별도 secret manager와 백업 정책으로 관리해야 합니다.

## 4. 기타 보안 지표
- **CORS 설정 (🟢 안전)**: `localhost` 및 `wa-pnu.duckdns.org`로 화이트리스트가 적절히 제한되어 있어 브라우저 기반의 무분별한 API 탈취를 방지합니다.
- **권한 제어 (🟢 안전)**: 어드민 페이지 접근 시 백엔드 단에서 JWT 토큰과 `ADMIN_EMAILS` 환경 변수를 교차 검증하여 권한 분리를 적절히 하고 있습니다.
